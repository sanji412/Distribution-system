## 2. 项目总体需求分析

### 2.1 项目背景

传统单体系统在业务规模扩大后容易出现模块耦合高、部署不灵活、服务扩展困难、故障影响范围大等问题。企业级系统通常会将业务按领域拆分为多个微服务，通过注册中心、网关、远程调用、分布式事务、限流降级等组件完成服务治理。

本项目以分销与订单履约为业务背景，选择商品、库存、订单、支付、物流、AI 客服等典型业务场景作为训练对象。项目先通过单体应用实现核心业务闭环，再逐步拆分为多个微服务，最终形成具备演示价值的企业级微服务系统。

### 2.2 项目建设目标

本项目应完成以下目标：

1. 完成商品、库存、订单、支付、AI 对话等基础业务数据建模。
2. 在 Day1 单体项目中跑通“创建订单 -> 扣减库存 -> 查询订单”的基础业务链路。
3. 在 Day2 将单体系统按 DDD 领域边界拆分为用户、商品、库存、订单、支付 5 个业务服务。
4. 接入 Nacos，实现服务注册发现与配置管理。
5. 接入 OpenFeign，实现订单服务对库存、商品、支付服务的远程调用。
6. 接入 Gateway，实现统一入口、路由转发、跨域处理和基础鉴权。
7. 接入 Seata AT 模式，实现订单、库存、支付之间的分布式事务一致性。
8. 接入 Sentinel，实现核心接口限流、熔断和降级演示。
9. 接入 DeepSeek API，实现订单物流查询、搭配推荐、库存预警、热销趋势等 AI 客服能力。
10. 完成 Vue3 前端页面或运行演示页面，展示服务治理、订单履约、数据看板、AI 客服和系统监控效果。

### 2.3 项目演进方式

项目不是两个互不相关的工程，而是一条渐进式演进路线。

Day1 阶段先完成单体项目，使用一个 SpringBoot 应用和一个 `distribution_db` 数据库，把基础业务流程跑通。Day2 开始基于 Day1 代码进行微服务拆分，将业务代码按领域迁移到不同服务，并将数据库从单库拆分为多个业务库。

推荐代码管理方式如下：

| 阶段 | 分支 | tag | 说明 |
| --- | --- | --- | --- |
| Day1 | `day1-monolith` | `day1-complete` | 单体项目，保留可运行基线 |
| Day2 | `day2-microservices` | `day2-complete` | 拆分为 5 个业务服务 |
| Day3 | `day3-nacos` | `day3-complete` | 接入 Nacos 注册与配置 |
| Day4 | `day4-openfeign` | `day4-complete` | 接入 OpenFeign 远程调用 |
| Day5 | `day5-gateway` | `day5-complete` | 接入 Gateway 网关 |
| Day6 | `day6-vue3` | `day6-complete` | 完成 Vue3 前端联调 |
| Day7 | `day7-seata` | `day7-complete` | 接入 Seata 分布式事务 |
| Day8 | `day8-sentinel` | `day8-complete` | 接入 Sentinel 限流降级 |
| Day9 | `day9-ai` | `day9-complete` | 接入 DeepSeek AI 客服 |

分支用于继续开发，tag 用于固定保存每天完成版，便于阶段验收和问题回溯。

### 3.2 普通用户

主要操作包括：

- 浏览商品
- 创建订单
- 查询订单状态
- 查询物流信息
- 通过 AI 客服咨询订单、物流或商品推荐

## 4. 功能需求分析

### 4.1 用户中心

用户中心负责系统账号与身份数据管理，是 Gateway 鉴权和业务数据关联的基础。

功能需求：

- 支持用户账号数据维护
- 支持管理员和普通用户角色区分
- 支持账号启用和禁用状态
- 支持通过用户名查询用户信息
- 后续微服务阶段为网关 JWT 鉴权提供用户数据依据

核心数据：

- 用户 ID
- 用户名
- 密码
- 昵称
- 角色
- 状态
- 手机号

### 4.2 商品分销中心

商品分销中心负责商品基础信息、分类、价格、安全库存和用户浏览历史，是订单创建、库存预警和 AI 推荐的数据来源。

功能需求：

- 商品新增、查询、修改、删除
- 商品上下架管理
- 商品分类查询
- 商品 SKU 编码维护
- 商品安全库存阈值配置
- 用户浏览历史记录
- 为 AI 搭配推荐提供浏览数据
- 为库存预警提供安全库存阈值

核心数据：

- 商品 ID
- 商品名称
- 分类
- 价格
- SKU 编码
- 商品描述
- 上下架状态
- 安全库存阈值
- 用户浏览历史

### 4.3 库存中心

库存中心负责仓库和库存管理，是订单履约链路中最关键的数据一致性参与方之一。

功能需求：

- 仓库信息维护
- 查询商品库存
- 查询多仓库库存
- 扣减库存
- 库存回滚
- 库存不足异常处理
- 库存预警
- 微服务阶段支持两个库存服务实例，演示负载均衡

核心场景：

- 正常下单时扣减库存成功
- 库存不足时抛出异常
- 分布式事务回滚时恢复库存
- 商品库存低于安全库存时触发预警

核心数据：

- 仓库 ID
- 仓库名称
- 仓库地址
- 商品 ID
- 当前库存数量

### 4.4 订单中心

订单中心负责订单全生命周期管理，是项目业务主链路和微服务调用链路的核心。

功能需求：

- 创建订单
- 查询订单列表
- 根据订单号查询订单详情
- 记录订单明细
- 维护订单状态
- 维护收货人信息
- 维护物流信息
- 调用库存服务扣减库存
- 调用支付服务创建支付单
- 作为 Seata 全局事务发起方
- 承载 AI 客服接口

订单状态包括：

- 待支付
- 已支付
- 已发货
- 已完成
- 库存不足

核心业务链路：

1. 用户提交订单。
2. 订单服务创建订单主表和订单明细。
3. 订单服务调用库存服务扣减库存。
4. 订单服务调用支付服务创建支付单。
5. 成功时提交事务。
6. 失败时回滚订单和库存数据。

### 4.5 支付中心

支付中心负责支付单创建、支付回调和支付状态同步，是订单履约链路中的交易状态支撑模块。

功能需求：

- 创建支付单
- 根据订单号查询支付单
- 处理支付回调
- 更新支付状态
- 支付成功后同步订单状态
- 支付失败时记录失败原因

支付状态包括：

- 待支付
- 支付成功
- 支付失败

核心数据：

- 支付单号
- 订单号
- 用户 ID
- 支付金额
- 支付方式
- 支付状态
- 回调报文
- 回调时间

### 4.6 履约配送

履约配送不单独拆分为独立服务，归属于订单中心管理，主要用于订单列表、物流查询和 AI 客服场景。

功能需求：

- 维护物流公司
- 维护物流单号
- 维护物流状态
- 维护当前位置
- 维护预计送达时间
- 支持订单物流查询
- 支持 AI 根据物流数据生成自然语言回复

物流状态包括：

- 待发货
- 运输中
- 已签收

### 4.7 AI 智能客服

AI 智能客服内嵌于订单中心，不单独拆分为微服务。它通过调用 DeepSeek API，将订单、物流、商品、库存等业务数据转换为自然语言回复。

功能需求：

- 订单物流问答
- 商品搭配推荐
- 库存预警问答
- 热销趋势建议
- AI 对话记录保存
- AI 调用次数统计
- 前端展示客服对话窗口和推荐卡片

典型问题：

- “我的订单 DD202505190001 到哪了？”
- “从北京仓发货到上海浦东要多久？”
- “推荐几款和机械键盘搭配的配件。”
- “库存不足的商品有哪些？”
- “近 7 天哪些商品销量增长快？”

服务治理模块主要用于最终演示，不一定需要新增业务表。该模块可以从 Nacos、Gateway、Sentinel 或后端模拟接口获取数据。

## 5. 非功能需求分析

### 5.1 可运行性

每个阶段的项目都应保持可运行状态。Day1 单体项目应能通过一个 SpringBoot 应用启动，并连接 `distribution_db`。Day2 之后各微服务应能独立启动，并能够通过接口完成跨服务调用。

### 5.2 可演示性

项目最终必须能够在答辩现场清晰展示以下能力：

- 业务链路可跑通
- 微服务已注册
- Gateway 路由可用
- OpenFeign 调用成功
- Seata 成功提交和失败回滚可演示
- Sentinel 限流规则可展示
- AI 客服能结合业务数据回复

### 5.3 数据一致性

订单、库存和支付之间存在强业务关联。单体阶段使用本地事务保证一致性；微服务阶段使用 Seata AT 模式保证跨服务事务一致性。

### 5.4 可扩展性

系统按业务域拆分后，应支持未来继续扩展物流服务、营销服务、结算服务等模块。但本次实训不扩展额外业务，避免超出课时范围。

### 5.5 易维护性

代码应按 Controller、Service、Mapper、Entity、DTO 等层次组织。数据库表命名和字段命名应保持清晰，接口返回格式应统一，便于后续前后端联调和答辩说明。

### 5.6 安全性

本项目只实现实训所需的基础安全能力，不做复杂权限体系。微服务阶段 Gateway 可实现 JWT 基础鉴权，未登录请求返回 401，普通用户和管理员根据角色进行简单区分。

## 6. 技术架构分析

### 6.1 Day1 单体架构

Day1 使用单体架构，目标是先完成业务闭环。

技术组成：

- SpringBoot
- MyBatis-Plus
- MySQL
- Lombok
- Postman

运行方式：

- 一个 SpringBoot 应用
- 一个 `distribution_db` 数据库
- 一个端口，默认 `8080`

Day1 重点：

- 建库建表
- 完成商品、库存、订单、支付等基础 CRUD
- 完成创建订单和扣减库存
- 完成订单查询
- 保留可运行版本并创建 `day1-monolith` 分支和 `day1-complete` tag

### 6.2 Day2 之后微服务架构

Day2 开始将单体系统拆分为多个服务。

最终服务规划：

| 服务名称 | 端口 | 数据库 | 核心职责 |
| --- | --- | --- | --- |
| `user-center` | 8001 | `user_db` | 用户账号、角色、鉴权数据 |
| `product-center` | 8002 | `product_db` | 商品信息、分类、安全库存、浏览历史 |
| `stock-center` | 8003/8004 | `stock_db` | 仓库库存、库存扣减、库存回滚 |
| `order-center` | 8005 | `order_db` | 订单生命周期、物流履约、AI 客服 |
| `pay-center` | 8006 | `pay_db` | 支付单、支付回调、支付状态 |
| `gateway-service` | 9000 | 无独立业务库 | 统一入口、路由、跨域、鉴权 |

### 6.3 核心组件职责

| 组件 | 作用 | 项目使用场景 |
| --- | --- | --- |
| Nacos | 服务注册发现、配置中心 | 管理 5 个业务服务和 1 个网关 |
| Gateway | 统一网关 | `/api/user`、`/api/product`、`/api/stock`、`/api/order`、`/api/pay` 路由转发 |
| OpenFeign | 远程服务调用 | 订单服务调用库存服务、商品服务、支付服务 |
| Seata | 分布式事务 | 订单、库存、支付跨库一致性 |
| Sentinel | 限流降级 | 库存扣减、订单创建、支付回调、商品列表限流 |
| Redis | 缓存与计数 | 热点商品缓存、库存预热、服务调用量统计 |
| DeepSeek API | 大模型问答 | AI 客服、推荐、预警、趋势建议 |

## 7. 核心业务流程分析

### 7.1 正常订单履约流程

1. 用户选择商品并提交订单。
2. 订单服务生成订单主表记录，状态为待支付。
3. 订单服务生成订单明细记录。
4. 订单服务调用库存服务扣减库存。
5. 库存扣减成功后，订单服务调用支付服务创建支付单。
6. 全链路执行成功，事务提交。
7. 用户支付成功后，支付服务接收回调。
8. 支付服务更新支付单状态为支付成功。
9. 订单服务同步订单状态为已支付。
10. 仓库发货后更新物流状态为运输中。
11. 用户签收后订单状态更新为已完成。

### 7.2 库存不足回滚流程

1. 用户提交订单。
2. 订单服务创建订单上下文。
3. 订单服务调用库存服务扣减库存。
4. 库存服务发现库存不足，抛出业务异常。
5. 单体阶段通过本地事务回滚。
6. 微服务阶段通过 Seata 全局事务回滚。
7. 订单最终标记为库存不足或订单创建失败。
8. 库存数据恢复，支付单不生成或标记为支付失败。

演示重点：

- 库存不足商品：无线鼠标 - 罗技 M720
- 库存不足订单：`DD202505190004`
- 回滚说明：Seata AT 模式通过 `undo_log` 保存修改前镜像，并在异常时恢复数据

### 7.3 AI 客服流程

1. 用户在前端输入自然语言问题。
2. 后端接收问题并识别意图。
3. 如果是订单查询，则根据订单号查询订单和物流数据。
4. 如果是推荐问题，则查询浏览历史和商品数据。
5. 如果是库存预警，则查询库存和商品安全库存。
6. 后端将业务数据拼接成结构化 Prompt。
7. 调用 DeepSeek API 生成自然语言回复。
8. 保存 AI 对话记录。
9. 将回复返回前端展示。

### 7.4 Sentinel 限流降级流程

项目对核心接口设置限流规则：

| 接口 | 阈值 | 策略 |
| --- | --- | --- |

## 9. 数据库总体分析

### 9.1 数据库设计原则

本项目数据库设计遵循以下原则：

1. 先单体后分库：Day1 使用 `distribution_db`，Day2 后拆分为多个业务库。
2. 按领域划分：每个微服务拥有自己的数据库，避免跨库直接访问。
3. 表结构精简：保留实训演示需要的核心字段，不设计复杂营销、审计、财务和权限体系。
4. 适度冗余：订单表冗余商品名称、数量、金额等字段，方便订单列表展示。
5. 支撑事务：订单库、库存库、支付库创建 `undo_log` 表，支持 Seata AT 模式。
6. 支撑演示：模拟数据覆盖成功订单、待支付订单、已发货订单、已完成订单、库存不足订单、AI 对话等场景。

### 9.2 Day1 单体数据库

Day1 使用一个数据库：

```text
distribution_db
```

该数据库包含全部业务表：

| 表名 | 说明 |
| --- | --- |
| `sys_user` | 用户表 |
| `product` | 商品表 |
| `browse_history` | 用户浏览历史表 |
| `warehouse` | 仓库表 |
| `stock` | 库存表 |
| `order_main` | 订单主表 |
| `order_item` | 订单明细表 |
| `payment` | 支付单表 |
| `ai_chat_record` | AI 对话记录表 |
| `undo_log` | Seata 预留回滚日志表 |

Day1 单体项目重点验证业务是否正确，不重点验证服务治理。

### 9.3 微服务分库规划

Day2 后数据库垂直拆分为 5 个业务库：

| 数据库 | 对应服务 | 核心表 |
| --- | --- | --- |
| `user_db` | `user-center` | `sys_user` |
| `product_db` | `product-center` | `product`、`browse_history` |
| `stock_db` | `stock-center` | `warehouse`、`stock`、`undo_log` |
| `order_db` | `order-center` | `order_main`、`order_item`、`ai_chat_record`、`undo_log` |
| `pay_db` | `pay-center` | `payment`、`undo_log` |

Gateway 不需要独立业务数据库。

### 9.4 数据库演进说明

Day1：

- 建立 `distribution_db`
- 导入同库版建表语句和模拟数据
- 所有 Mapper 都连接同一个数据库
- 使用本地事务处理订单和库存

Day2：

- 建立 `user_db`、`product_db`、`stock_db`、`order_db`、`pay_db`
- 将 Day1 表按领域迁移到不同数据库
- 各微服务只连接自己的数据库
- 服务之间通过接口交互，禁止跨库直连

Day7：

- 在 `stock_db`、`order_db`、`pay_db` 中保留或创建 `undo_log`
- 使用 Seata AT 模式管理订单、库存、支付的跨库事务

## 13. 数据一致性分析

### 13.1 单体阶段一致性

Day1 单体项目中，订单、库存和支付表都在 `distribution_db` 中，可以通过 Spring 本地事务保证一致性。

典型做法：

- 创建订单
- 扣减库存
- 创建支付单
- 任意一步失败则整体回滚

### 13.2 微服务阶段一致性

Day2 之后，订单、库存、支付位于不同服务和不同数据库中，不能再依赖本地事务，需要使用 Seata 管理分布式事务。

事务参与方：

- `order-center`：TM，全局事务发起方
- `stock-center`：RM，库存扣减参与方
- `pay-center`：RM，支付单创建参与方
- Seata Server：TC，事务协调者

正常提交：

```text
order-center 开启全局事务
-> stock-center 扣减库存成功
-> pay-center 创建支付单成功
-> TC 通知各 RM 提交
-> 删除 undo_log
```

异常回滚：

```text
order-center 开启全局事务
-> stock-center 扣减库存失败
-> 抛出异常
-> TC 通知各 RM 回滚
-> RM 根据 undo_log 恢复数据
```

## 17. 开发注意事项

1. 运行演示页面是最终展示参考，页面中的部分 mock 数值与数据库初始化数据不完全一致，开发时应以数据库和实际接口为准。
2. Day1 应优先使用 `distribution_db`，不要一开始就强行拆成微服务。
3. Day2 后每个服务只访问自己的数据库，禁止跨库直连。
4. `order_db`、`stock_db`、`pay_db` 必须包含 `undo_log`，用于 Seata AT 模式。
5. AI 客服应尽量结合业务数据生成回复，不应只做固定话术。
6. 代码包名、配置文件中的 `type-aliases-package` 和实际 Java 包路径应保持一致。
7. 每天完成任务后应提交 Git commit，并创建对应 tag 保存阶段成果。
8. 最终答辩重点不是页面样式完全一致，而是能讲清楚业务链路和技术链路。

## 18. 总结

企业级智能分销与订单履约平台是一个以订单履约为主线、以微服务架构演进为训练目标的综合实训项目。项目先通过 Day1 单体应用建立业务基础，再在后续阶段逐步引入服务拆分、注册发现、远程调用、网关、分布式事务、限流降级和 AI 客服能力。

数据库设计围绕用户、商品、库存、订单、支付和 AI 对话展开。Day1 使用 `distribution_db` 保证快速起步，Day2 之后拆分为 5 个业务库以匹配微服务边界。订单、库存和支付是事务一致性的核心，Seata AT 模式和 `undo_log` 表是后续分布式事务演示的关键。

最终项目应能够清晰展示“业务可运行、服务可治理、事务可回滚、流量可保护、AI 可结合业务”的完整实训成果。
