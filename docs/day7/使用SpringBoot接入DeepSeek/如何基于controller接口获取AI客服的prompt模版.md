# 一、Prompt 设计核心规则

#### 1. 业务场景引入

电商平台每天有大量用户咨询：查物流、问售后、找商品、问活动。人工客服成本高、响应慢，而普通的 AI 对话存在三个致命问题：

- 回答随意，不符合品牌客服规范，语气不可控
- 无法对接真实业务数据（比如查不到用户真实的订单物流）
- 无法分类处理问题，所有问题都让 AI 自由发挥，容易出错

本节课的目标：用 Spring AI + 结构化 Prompt，打造一个**专业、可控、能对接业务**的电商智能客服。

#### 2. 技术实现全景图

~~~tex
  用户提问 	→ 意图识别+槽位提取 	→ 意图路由判断
     ↓
  通用咨询 	→ 直接用客服Prompt模板生成回复
     ↓
  业务查询 	→ 校验槽位→缺失则追问	→完整则调用业务接口→填充数据→生成动态Prompt→AI回复
     ↓
  返回自然语言的客服回复
~~~

#### 3.Prompt 五大核心规则

大模型默认是 “通用聊天模式”，而电商客服是 “专业岗位模式”。如果只说 “你是客服”，AI 会出现语气不对、超范围回答、泄露信息、随意承诺等问题。所以需要对大模型进行规范：

| 规则               | 说明                                                         | 反面错误示例           | 正面正确示例                                                 |
| ------------------ | ------------------------------------------------------------ | ---------------------- | ------------------------------------------------------------ |
| **角色人设明确**   | 固定身份、语气、称呼，保持品牌一致性                         | 你是客服，回答用户问题 | 你是「优选电商」的官方在线客服，称呼用户为「亲亲」，语气亲切耐心，符合电商服务规范 |
| **业务边界清晰**   | 明确规定能回答什么、不能回答什么，超出范围统一话术回复       | 回答用户的所有问题     | 仅可回答订单、物流、售后、商品、活动相关问题；与电商业务无关的问题，统一回复：「抱歉亲亲，我只能解答电商购物相关问题哦～」 |
| **回复规则具体**   | 规定回复长度、格式、禁止行为（比如不许骂人、不许承诺未公布的活动） | 好好回答用户           | 回复控制在 200 字以内，分点说明时使用数字序号；禁止向用户承诺平台未公示的优惠和补偿 |
| **输出可控可预测** | 关键信息必须按要求格式输出，不能自由发挥                     | 提取订单信息           | 从用户问题中提取订单号，只返回订单号数字，不要任何解释文字   |
| **上下文聚焦**     | 限定回答只基于给定信息，禁止编造数据                         | 帮我查物流             | 仅基于下方提供的物流信息回复用户，禁止编造物流状态和时间     |

# 二、结构化 Prompt 模板设计

#### 1. 为什么需要模板

每次调用 AI 都手写一长段提示词效率低、维护麻烦、效果不稳定。**模板 = 固定结构 + 变量占位符**，程序只需填充变量即可生成标准 Prompt，可复用、易修改、效果一致。

#### 2.电商客服基础模板的标准结构

~~~tex
【角色人设】
固定身份、语气、服务规范

【业务范围】
可解答的问题类型
不可解答的问题与兜底话术

【回复要求】
长度、格式、语气细节、禁止项

【参考信息】（可选，动态填充）
业务数据、订单信息、商品详情等

【用户当前问题】
{userMessage}
~~~

#### 3. 变量化设计

用 `{变量名}` 作为占位符，程序运行时动态替换内容，比如：

- `{userMessage}`：用户输入的问题
- `{orderId}`：用户的订单号
- `{logisticsInfo}`：从业务系统查询到的物流数据

#### 4. 已验证可用：电商客服通用模板

~~~tex
【角色人设】
你是优选电商的官方在线客服，称呼用户为「亲亲」，语气亲切、耐心、专业，使用生活化的口语表达，不要生硬官方。

【业务范围】
仅可解答商品咨询、物流查询、售后申请、活动规则四类问题。
超出以上范围的问题，统一回复：「抱歉亲亲，我只能解答购物相关的问题哦~」

【回复要求】
1. 回复简洁易懂，控制在150字以内
2. 涉及步骤时用数字序号分点说明
3. 绝对不可以编造平台规则、优惠活动、物流信息
4. 禁止与用户争吵、禁止使用不礼貌用语

【用户当前问题】
{userMessage}
~~~

#### 5. 实操：模板接入项目

在 `DeepSeekService` 中新增一个通用客服对话方法，将模板与用户问题拼接后调用 AI。

参考代码片段：

```java
/**
 * 通用电商客服对话
 * @param userMessage 用户问题
 * @return 客服回复
 */
public String DeepSeekService(String userMessage) {
    // 客服模板，{userMessage} 是占位符
    String promptTemplate = """
            【角色人设】
            你是优选电商的官方在线客服，称呼用户为「亲亲」，语气亲切、耐心、专业。
            
            【业务范围】
            仅可解答商品咨询、物流查询、售后申请、活动规则四类问题。
            超出范围统一回复：抱歉亲亲，我只能解答购物相关的问题哦~
            
            【回复要求】
            1. 回复简洁，150字以内
            2. 禁止编造物流、优惠等不存在的信息
            
            【用户当前问题】
            {userMessage}
            """;
    
    // 替换占位符
    String finalPrompt = promptTemplate.replace("{userMessage}", userMessage);
    
    return chatClient.prompt()
            .user(finalPrompt)
            .call()
            .content();
}
```

**自检标准**：调用该方法，测试无关问题能正确兜底，客服语气符合设定。



# 三、意图识别与槽位提取实现

#### 1. 核心概念

- **意图（Intent）**：用户提问的目的，也就是用户想做什么。比如 “我的快递到哪了” 的意图是「物流查询」。
- **槽位（Slot）**：完成这个意图必须的关键信息。比如物流查询必须要有「订单号」，没有订单号就查不到物流。

> 为什么必须做这一步？
>
> AI 不能直接查数据库、不能调用业务接口。必须先识别用户想干什么、有没有带齐关键信息，再决定是直接回复、还是追问信息、还是调用业务系统查数据。

#### 2. 支持的意图与槽位定义

| 意图编码            | 意图名称 | 必填槽位          | 说明                     |
| ------------------- | -------- | ----------------- | ------------------------ |
| `logistics_query`   | 物流查询 | orderId（订单号） | 用户查询订单物流状态     |
| `after_sales_apply` | 售后申请 | orderId、reason   | 用户申请退换货、退款     |
| `product_consult`   | 商品咨询 | 无                | 问商品参数、规格、用法等 |
| `activity_consult`  | 活动咨询 | 无                | 问优惠、满减、活动时间等 |
| `other`             | 其他     | 无                | 无法识别的意图或无关问题 |

#### 3. 意图槽位提取专用 Prompt 设计

核心要求：**让 AI 严格输出 JSON 格式，无多余文字**，方便程序解析。

~~~tex
你是电商系统的需求分析师，严格基于下方提供的【微服务清单】【核心建表SQL】【Controller层接口文档】，生成C端AI客服的语义提取规则。

【硬性约束】
1.  只基于提供的材料推导，严禁新增任何文档里没有的接口、字段和业务能力
2.  一个用户侧查询接口对应一个核心意图，意图命名和接口功能对齐
3.  槽位字段名必须和Controller接口的入参名称完全一致，必填/可选属性和接口保持统一
4.  剔除鉴权类公共参数（如token、userId），只保留用户对话中会提到的业务参数
5.  必须补充other兜底意图，覆盖所有接口外的无关问题

【输出格式】
### 一、可识别意图列表
| 意图英文标识 | 意图中文名称 | 对应接口 | 触发场景说明 |
|-------------|--------------|----------|--------------|

### 二、分意图槽位提取规则
#### 1. 意图英文标识（中文名称）
- 字段名1：必填/可选，字段业务说明
- 字段名2：必填/可选，字段业务说明

---
【微服务清单】
（粘贴微服务名称+职责，示例：
- 订单服务：负责订单、物流相关业务
- 商品服务：负责商品、库存相关业务）

【核心建表SQL】
（粘贴核心表建表语句，只保留字段名和注释，用于校验字段合理性）

【Controller层用户侧接口文档】
（粘贴你的接口文档，建议按以下格式整理，示例：
   接口名称：订单物流查询
   接口路径：/api/order/logistics
   请求方式：GET
   入参列表：
   - orderId：String，必填，订单编号
   - userId：Long，必填，用户ID（鉴权用）
）
~~~

# 四、动态Prompt生成

#### 1. 完整客服业务流程设计

~~~tex
用户发送消息
    ↓
调用意图识别+槽位提取
    ↓
根据意图路由分发：
├─ 商品咨询/活动咨询 → 直接用通用客服Prompt模板 → AI生成回复
├─ 物流查询 → 检查是否有orderId
│   ├─ 无 → 返回追问话术：「亲亲，请提供一下你的订单号哦~」
│   └─ 有 → 调用物流接口（模拟）获取真实数据 → 填充到Prompt模板 → AI生成自然回复
├─ 售后申请 → 检查槽位完整性 → 缺失则追问 → 完整则引导下一步
└─ 其他 → 返回通用兜底话术
    ↓
返回最终客服回复
~~~

#### 2. 核心：动态 Prompt 生成逻辑

对于需要业务数据的场景，**把查询到的真实数据填充到 Prompt 中，让 AI 基于真实数据组织语言**，既保证信息准确，又保证回复自然。

物流查询场景的动态 Prompt 模板示例：

~~~tex
你是电商平台的客服语义解析专家，严格按照以下规则解析用户的提问，只输出标准JSON，禁止添加任何解释、问候、说明文字。

【可识别意图说明】
1. order_logistics：订单物流查询，用户询问订单发货状态、物流轨迹、收货时间
2. goods_stock：商品库存查询，用户询问商品是否有货、库存数量
3. return_refund：退换货咨询，用户询问退货、退款申请规则
4. other：无关问题，不在上述业务范围内的所有提问

【槽位提取规则】
- order_logistics：提取 order_id（订单号，必填）
- goods_stock：提取 goods_name（商品名称，必填）
- return_refund：提取 order_id（订单号，必填）、goods_id（商品ID，可选）
必填槽位缺失时，is_complete 标记为 false，并生成追问话术。

【输出格式】
严格输出纯JSON，无任何多余字符，字段定义如下：
{
  "intent": "意图英文标识",
  "slots": {
    "槽位字段名": "提取到的值，未提取到则为null"
  },
  "is_complete": true/false,
  "reply_tip": "参数完整为null；缺失则返回亲切的追问话术；无关问题返回「抱歉，我暂时无法解答这个问题哦~」"
}

用户提问：{{用户输入内容}}
~~~

#### 3.语句"用户提问：{{用户输入内容}}"的作用

`用户提问：{{用户输入内容}}` 是整段语义解析 Prompt 的**动态任务入口 + 变量占位符**，是模板里唯一的可变部分。前面所有的「意图规则、槽位规则、输出格式」都是固定不变的约束条件，而这一行的作用是：**明确告诉大模型「你要解析的具体对象是这句话」，同时作为代码拼接的动态变量位**。分点详解 4 个核心作用：

##### 1. 明确解析目标，划定任务边界

大模型会严格区分「规则指令」和「待处理内容」。前面的所有文字都是告诉 AI「你该按什么规则做事」，但 AI 并不知道要解析哪一句话。

- 如果没有这一行，AI 不知道处理对象，要么输出空结果，要么反过来解读规则本身；
- 加上「用户提问：xxx」的固定格式，AI 就能精准识别：冒号后面的内容才是我需要解析的目标，前面的都是我要遵守的规则。

这是指令类 Prompt 的标准结构：**规则在前，待处理内容在后**，边界清晰，避免混淆。

##### 2. 模板变量占位，对接后端代码

`{{用户输入内容}}` 是一个**模板占位符**，不是最终会发给大模型的文字。

在 SpringBoot 项目的实际调用中，代码会先读取这段完整的 Prompt 模板，然后把前端传来的真实用户问题（比如 “我的订单 20240601 发货了吗”）替换掉这个占位符，再把拼接完成的完整文本发给大模型。

##### 3. 强化指令收尾，减少多余输出

把待处理内容放在最后，符合大模型的指令遵循习惯：先接收全部规则，再拿到任务目标，然后直接输出结果。

如果把用户问题放在最前面，大模型很容易先按自己的常识回答问题，再看后面的规则，导致输出不符合要求；而「规则在前，问题在后」的结构，能让 AI 先记住约束，再处理内容，输出 JSON 的稳定性会大幅提升，也更不容易出现 “好的，我来解析一下...” 这类多余的解释文字。

##### 4. 固定输入格式，提升解析准确率

每次调用都用「用户提问：xxx」的统一格式结尾，大模型会形成稳定的识别模式：只要看到这个前缀，就知道后面是待解析的用户输入。

哪怕用户的问题里包含 “订单”“库存” 等和规则里重复的关键词，AI 也能准确区分「规则里的定义」和「用户问题里的内容」，不会出现把规则里的示例当成用户提问来解析的低级错误。

# 五、Java代码生成

由于实现SpringBoot接入DeepSeek的方式不止一种，并且不同版本依赖会有不兼容现象，所以在生成java代码时，要时刻提示AI当前所使用的技术栈和版本，提示词如下：

~~~tex
强制技术约束（必须100%遵守）:
1. 基础框架：Spring Boot 3.2.12 正式版，JDK 版本为 21
2. AI 依赖：Spring AI 1.0.8 正式版，依赖 artifactId 固定为 spring-ai-openai-spring-boot-starter
3. 对接规范：
   - 对接 DeepSeek 大模型，API 基础地址为 https://api.deepseek.com
   - 默认对话模型为 deepseek-chat
   - 配置项命名遵循 Spring AI 官方标准，前缀为 spring.ai.openai
~~~
